# Architecture

How this service is built. The statement (`README.md`, `enunciado.pdf`) and `openapi.yaml` define **what** it does; this document defines **how**. If a task needs something this document does not cover, stop and ask instead of inventing it.

## 1. Stack

| Concern | Choice |
|---|---|
| Runtime | Node ≥ 22, TypeScript strict, run directly with `tsx` (no build output); `tsc --noEmit` only typechecks |
| HTTP | Express + Zod |
| Data | PostgreSQL through Prisma |
| Dates | Luxon |
| Tests | Vitest |
| Lint | ESLint, relative imports forbidden |

Dependency direction:

- `domain` imports nothing from `app` or `infra`.
- `app` imports `domain`, its own `ports.ts`, and **one** thing from infra: `now` from `@/infra/clock`.
- `infra` imports anything.
- Routes import ready use cases from `@/infra/use-cases/*`; they never import `app` factories or repositories.

## 3. Conventions

1. **Absolute imports only**: `@/domain/...`, `@/app/...`, `@/infra/...`. Never `./` or `../`.
2. **One named-object argument** for every use case, repository method and domain function with more than a bare value: `getAppointment({ id })`. The only exception is `parseReply(text)` and `isValidTimezone(timezone)`.
3. **Expected failures are values**: use cases return `Result<T, E>` where `E` is a union of string literals. `throw` is only for bugs and infrastructure failures; the HTTP error handler turns those into 500.
4. **Never `new Date()` for the current time.** Call `now()` from `@/infra/clock`, in the app layer only. Domain functions receive the instant as an argument named by intent (`notBefore`, `at`, `attemptedAt`).
5. **UTC everywhere.** Instants are `Date` in code and `timestamptz` in the database. The clinic timezone is used in exactly two places: `scheduleReminder` and `reminderText`.
6. **The domain is pure**: no database, clock, network or `process.env`.
7. **Use cases are closures**: `makeX(deps)` returns `x(input)`. `deps` lists exactly what that use case uses.
8. **No `any`, no non-null `!`.** `as` only where external data enters (raw SQL rows), right next to the query.
9. **Zod schemas are the source of input types** (`z.infer`); domain and app types are written by hand and do not depend on Prisma types. Repositories map Prisma rows to domain types.
10. **Exhaustiveness**: every `switch` over a union ends in a `never` check, and error-to-status maps are typed `Record<ErrorUnion, …>` so a new error does not compile until it is mapped.

## 4. Data model

Five tables. All ids are UUIDs generated by the database. The reminder id is also the provider `Idempotency-Key`.

```prisma
enum AppointmentStatus { scheduled confirmed cancelled }
enum ReminderStatus    { pending sent failed skipped cancelled }
enum SkipReason        { too_late no_phone opted_out }

model Clinic {
  id       String @id @default(uuid()) @db.Uuid
  name     String
  timezone String
  @@map("clinics")
}

model Patient {
  id               String  @id @default(uuid()) @db.Uuid
  clinicId         String  @map("clinic_id") @db.Uuid
  name             String
  phone            String?
  acceptsReminders Boolean @map("accepts_reminders")
  clinic           Clinic  @relation(fields: [clinicId], references: [id])
  @@index([phone])
  @@map("patients")
}

model Appointment {
  id        String            @id @default(uuid()) @db.Uuid
  clinicId  String            @map("clinic_id") @db.Uuid
  patientId String            @map("patient_id") @db.Uuid
  startsAt  DateTime          @map("starts_at") @db.Timestamptz(3)
  status    AppointmentStatus @default(scheduled)
  clinic    Clinic            @relation(fields: [clinicId], references: [id])
  patient   Patient           @relation(fields: [patientId], references: [id])
  reminders Reminder[]
  @@index([patientId])
  @@map("appointments")
}

model Reminder {
  id            String         @id @default(uuid()) @db.Uuid
  seq           Int            @unique @default(autoincrement())   // creation order
  appointmentId String         @map("appointment_id") @db.Uuid
  scheduledFor  DateTime       @map("scheduled_for") @db.Timestamptz(3)    // fixed: when it was due
  nextAttemptAt DateTime       @map("next_attempt_at") @db.Timestamptz(3)  // internal: moves on each retry
  status        ReminderStatus
  attempts      Int            @default(0)                          // calls made to the provider
  sentAt        DateTime?      @map("sent_at") @db.Timestamptz(3)
  skipReason    SkipReason?    @map("skip_reason")
  appointment   Appointment    @relation(fields: [appointmentId], references: [id])
  @@index([appointmentId, seq])
  @@map("reminders")
}

model InboundMessage {
  messageId  String   @id @map("message_id")
  fromPhone  String   @map("from_phone")
  text       String
  receivedAt DateTime @map("received_at") @db.Timestamptz(3)
  @@map("inbound_messages")
}
```

Added by hand to the migration SQL, because `schema.prisma` cannot express them:

```sql
-- Rule 1: at most one live reminder per appointment
CREATE UNIQUE INDEX reminders_one_pending_per_appointment ON reminders (appointment_id) WHERE status = 'pending';
-- The queue: what the send pass scans
CREATE INDEX reminders_due ON reminders (next_attempt_at) WHERE status = 'pending';
-- Columns that only make sense in one status
ALTER TABLE reminders ADD CONSTRAINT reminders_skip_reason_iff_skipped CHECK ((status = 'skipped') = (skip_reason IS NOT NULL));
ALTER TABLE reminders ADD CONSTRAINT reminders_sent_at_iff_sent       CHECK ((status = 'sent') = (sent_at IS NOT NULL));
```

There is a single migration, created in T0 with all five tables. No later task adds one.

Invariants the code relies on:

- A `pending` reminder always belongs to an appointment that is not cancelled (cancelling cancels it in the same transaction). The send pass therefore never checks the appointment status.
- `scheduled_for` never changes after insert. `next_attempt_at` starts equal to it.
- Reminders are ordered by `seq`, never by a timestamp (the test clock can freeze time).

These four entity types are exactly the response bodies of `openapi.yaml`; routes return them as they are and `res.json` serialises each `Date` as UTC with `Z`. `seq` and `nextAttemptAt` never leave the repositories.

## 6. Domain

```ts
// schedule.ts — when the reminder goes out (rules 2 to 5)
scheduleReminder(input: { startsAt: Date; timezone: string; notBefore: Date; quietHours: QuietHours }): ReminderPlan

// schedule.ts — what to do right before sending (rules 5 and 6). Check order: too_late, no_phone, opted_out
beforeSend(input: { startsAt: Date; phone: string | null; acceptsReminders: boolean; at: Date }): SendDecision

// message.ts — the exact text (rule 7), date and time in the clinic timezone
reminderText(input: { patientName: string; clinicName: string; startsAt: Date; timezone: string }): string

// retry.ts — what happens after an attempt. `attempt` is the one just made: 1, 2 or 3
afterAttempt(input: { outcome: SendOutcome; attempt: number; attemptedAt: Date }): AttemptResult

// reply.ts
parseReply(text: string): Reply | null

// timezone.ts
isValidTimezone(timezone: string): boolean      // IANAZone.isValidZone
```

Rules inside each function:

- **`scheduleReminder`**: same local time on the previous calendar day in the clinic timezone (`minus({ days: 1 })`, not 24 h); moved out of quiet hours; if that is before `notBefore`, use `notBefore` and move out of quiet hours again; `too_late` when the result is not strictly before `startsAt`. Quiet hours: at `from` o'clock sending is already forbidden, at `until` o'clock it is allowed.
- **`beforeSend`**: `too_late` when `at >= startsAt`; `no_phone` when `phone` is null; `opted_out` when `acceptsReminders` is false.
- **`afterAttempt`**: `delivered` → `sent` with `sentAt = attemptedAt`; `rejected` → `failed`; `not_delivered` or `unknown` → attempt 1: `pending` at +1 min, attempt 2: `pending` at +5 min, attempt 3: `failed`. Retries ignore quiet hours.
- **`parseReply`**: strip accents, lowercase, trim anything that is not a letter or digit from both ends; `si` → `confirm`, `no` → `cancel`, anything else → `null`.

Reference implementation of the scheduling rule (verified against the DST and Canary cases of the statement):

```ts
export function scheduleReminder(input: { startsAt: Date; timezone: string; notBefore: Date; quietHours: QuietHours }): ReminderPlan {
  const start    = DateTime.fromJSDate(input.startsAt,  { zone: input.timezone });
  const earliest = DateTime.fromJSDate(input.notBefore, { zone: input.timezone });
  let at = outOfQuietHours(start.minus({ days: 1 }), input.quietHours);
  if (at < earliest) at = outOfQuietHours(earliest, input.quietHours);
  return { scheduledFor: at.toJSDate(), skipReason: at < start ? null : 'too_late' };
}

function outOfQuietHours(t: DateTime, { from, until }: QuietHours): DateTime {
  const crossesMidnight = from > until;
  const isQuiet = crossesMidnight ? t.hour >= from || t.hour < until : t.hour >= from && t.hour < until;
  if (!isQuiet) return t;
  const end = t.set({ hour: until, minute: 0, second: 0, millisecond: 0 });
  return crossesMidnight && t.hour >= from ? end.plus({ days: 1 }) : end;
}
```

## 7. Ports (`app/ports.ts`)

What the use cases need from the outside. `infra` implements them.

```ts
export type ClinicRepository = {
  create(input: { name: string; timezone: string }): Promise<Clinic>;
  findById(input: { id: string }): Promise<Clinic | null>;
};

export type PatientRepository = {
  create(input: { clinicId: string; name: string; phone: string | null; acceptsReminders: boolean }): Promise<Patient>;
  findById(input: { id: string }): Promise<Patient | null>;
};

export type AppointmentRepository = {
  /** Inserts the appointment and its first reminder atomically. */
  create(input: { clinicId: string; patientId: string; startsAt: Date; reminder: ReminderPlan }): Promise<Appointment>;
  findById(input: { id: string }): Promise<Appointment | null>;
  /** SELECT … FOR UPDATE. Only inside a transaction. */
  lockById(input: { id: string }): Promise<Appointment | null>;
  update(input: { id: string; startsAt?: Date; status?: AppointmentStatus }): Promise<void>;
  /** Locks the appointment of the last reminder sent to that phone, among appointments
      that are not cancelled and start after `at`. Only inside a transaction. */
  lockLastRemindedByPhone(input: { phone: string; at: Date }): Promise<{ id: string } | null>;
};

export type DueReminder = {
  id: string;
  attempts: number;
  appointment: { startsAt: Date };
  patient: { name: string; phone: string | null; acceptsReminders: boolean };
  clinic: { name: string; timezone: string };
};

export type ReminderSettlement =
  | { status: 'sent'; attempts: number; sentAt: Date }
  | { status: 'failed'; attempts: number }
  | { status: 'pending'; attempts: number; nextAttemptAt: Date }
  | { status: 'skipped'; skipReason: SkipReason };

export type ReminderRepository = {
  create(input: { appointmentId: string; plan: ReminderPlan }): Promise<void>;
  /** pending → cancelled for that appointment. No-op when there is none. */
  cancelPending(input: { appointmentId: string }): Promise<void>;
  /** Oldest pending reminder with next_attempt_at <= at, FOR UPDATE SKIP LOCKED. Only inside a transaction. */
  lockNextDue(input: { at: Date }): Promise<DueReminder | null>;
  settle(input: { id: string; settlement: ReminderSettlement }): Promise<void>;
};

export type InboundMessageRepository = {
  /** false when that messageId was already stored. */
  insertIfNew(input: { messageId: string; from: string; text: string; receivedAt: Date }): Promise<boolean>;
};

export type Repositories = {
  clinics: ClinicRepository;
  patients: PatientRepository;
  appointments: AppointmentRepository;
  reminders: ReminderRepository;
  inboundMessages: InboundMessageRepository;
};

/** Runs `work` in one database transaction, with repositories bound to it. */
export type Transaction = <T>(work: (repos: Repositories) => Promise<T>, options?: { timeoutMs?: number }) => Promise<T>;

export type ProviderClient = {
  sendMessage(input: { to: string; text: string; idempotencyKey: string }): Promise<SendOutcome>;
};
```

Repository rules:

- A `ReminderPlan` is stored as `pending` with `next_attempt_at = scheduled_for` when `skipReason` is null, and as `skipped` with that reason otherwise.
- An id that is not a UUID is "not found": `findById` and `lockById` return `null` without querying.
- Every `Appointment` returned carries its reminders ordered by `seq`.

## 8. Use cases

Each `makeX` takes only the dependencies listed. Signatures are those of the returned function.

### `createClinic` — deps `{ clinics }`

```ts
(input: { name: string; timezone: string }) => Promise<Result<Clinic, 'INVALID_TIMEZONE'>>
```
`isValidTimezone` → insert.

### `createPatient` — deps `{ clinics, patients }`

```ts
(input: { clinicId: string; name: string; phone: string | null; acceptsReminders: boolean }) => Promise<Result<Patient, 'CLINIC_NOT_FOUND'>>
```

### `createAppointment` — deps `{ clinics, patients, appointments, quietHours }`

```ts
(input: { clinicId: string; patientId: string; startsAt: Date }) =>
  Promise<Result<Appointment, 'CLINIC_NOT_FOUND' | 'PATIENT_NOT_FOUND' | 'PATIENT_NOT_IN_CLINIC' | 'STARTS_AT_NOT_FUTURE'>>
```
1. Clinic missing → `CLINIC_NOT_FOUND`. Patient missing → `PATIENT_NOT_FOUND`. Patient of another clinic → `PATIENT_NOT_IN_CLINIC`.
2. `const at = now()`; `startsAt <= at` → `STARTS_AT_NOT_FUTURE`.
3. `scheduleReminder({ startsAt, timezone: clinic.timezone, notBefore: at, quietHours })`.
4. `appointments.create(...)` with that plan. No explicit transaction: the insert is atomic.

### `getAppointment` — deps `{ appointments }`

```ts
(input: { id: string }) => Promise<Result<Appointment, 'APPOINTMENT_NOT_FOUND'>>
```

### `rescheduleAppointment` — deps `{ transaction, quietHours }`

```ts
(input: { id: string; startsAt: Date }) =>
  Promise<Result<Appointment, 'APPOINTMENT_NOT_FOUND' | 'STARTS_AT_NOT_FUTURE' | 'APPOINTMENT_CANCELLED'>>
```
In one transaction:
1. `appointments.lockById`. Missing → `APPOINTMENT_NOT_FOUND`.
2. `startsAt <= now()` → `STARTS_AT_NOT_FUTURE`. Status `cancelled` → `APPOINTMENT_CANCELLED`. An appointment that already started **can** be rescheduled.
3. Same instant as the current `startsAt` → return the appointment unchanged (rule 1: no second reminder for the same time).
4. `reminders.cancelPending`; `appointments.update({ id, startsAt, status: 'scheduled' })`; `scheduleReminder` with the clinic timezone; `reminders.create`. The new reminder is created even when the previous one was already sent.
5. Return `appointments.findById`.

### `cancelAppointment` — deps `{ transaction }`

```ts
(input: { id: string }) => Promise<Result<Appointment, 'APPOINTMENT_NOT_FOUND'>>
```
In one transaction: lock; missing → error; already cancelled → return it unchanged; otherwise `reminders.cancelPending`, `appointments.update({ id, status: 'cancelled' })`, return the fresh appointment.

### `runReminderPass` — deps `{ transaction, provider }`

```ts
() => Promise<{ processed: number }>
```
Calls an internal `processNextReminder(): Promise<boolean>` until it returns `false`, counting the `true`s. Each call is one transaction with `timeoutMs: 15_000` (the Prisma default of 5 s equals the provider timeout and would abort mid-call):

1. `reminders.lockNextDue({ at: now() })`. None → `false`.
2. `beforeSend({ startsAt, phone, acceptsReminders, at: now() })`. `skip` → `settle` as `skipped` with the reason, without calling the provider → `true`.
3. `provider.sendMessage({ to: phone, text: reminderText(...), idempotencyKey: reminder.id })`.
4. `afterAttempt({ outcome, attempt: reminder.attempts + 1, attemptedAt: now() })` → `settle` with `attempts + 1` → `true`.

Why this is safe:

- The row lock is held during the provider call, so two concurrent passes never send the same reminder; `SKIP LOCKED` makes the second pass move on instead of waiting.
- A reminder that fails stays `pending` with a later `next_attempt_at`, so the same pass does not pick it again. A retry is never a wait inside the pass.
- `beforeSend` runs before every attempt, so retries are also dropped as `too_late`.
- If the process dies after the provider accepted, the reminder is still `pending`; the next pass resends with the same `Idempotency-Key` and the provider deduplicates.
- The pass locks only the reminder row, never the appointment, so it cannot deadlock with reschedule or cancel (which lock the appointment first and then wait for the reminder).

### `handleInboundMessage` — deps `{ transaction }`

```ts
(input: { messageId: string; from: string; text: string; receivedAt: Date }) => Promise<'applied' | 'duplicate' | 'ignored'>
```
In one transaction:
1. `inboundMessages.insertIfNew` (`ON CONFLICT DO NOTHING`). `false` → `duplicate`.
2. `parseReply(text)`. `null` → `ignored`.
3. `appointments.lockLastRemindedByPhone({ phone: from, at: now() })`. None → `ignored`.
4. `confirm` → `update({ id, status: 'confirmed' })`. `cancel` → `reminders.cancelPending` and `update({ id, status: 'cancelled' })`. → `applied`.

The message is stored in the same transaction that applies it: if applying fails, the provider's retry is processed again. The lookup is by phone, not by patient, because the same number can belong to several patients. A cancelled appointment is excluded from the lookup, so a SI after a NO is ignored.

### Wiring (`infra/use-cases/<feature>.ts`)

```ts

Queries with `FOR UPDATE` use `$queryRaw` on the transaction client.

## 9. HTTP

A route does three things: validate the body with Zod, call the use case, map the result.

- **Input**: dates are `z.string().datetime({ offset: true })` transformed to `Date` (a date without zone is 400). Phone is `^\+[1-9]\d{7,14}$` or `null`; a missing `phone` is `null`. `name` has at least one character.
- **Errors**: always `{ "error": "<message>" }`. Invalid body or malformed JSON → 400. Unknown route → 404. Unhandled exception → 500.
- **Path ids** are not validated by the route; a malformed one comes back from the use case as not found.

| Use-case error | Status |
|---|---|
| `INVALID_TIMEZONE`, `PATIENT_NOT_IN_CLINIC`, `STARTS_AT_NOT_FUTURE` | 400 |
| `CLINIC_NOT_FOUND`, `PATIENT_NOT_FOUND`, `APPOINTMENT_NOT_FOUND` | 404 |
| `APPOINTMENT_CANCELLED` | 409 |

| Endpoint | Use case | Success |
|---|---|---|
| `GET /health` | — (`SELECT 1` and migrations applied) | 200 |
| `POST /clinics` | `createClinic` | 201 |
| `POST /patients` | `createPatient` | 201 |
| `POST /appointments` | `createAppointment` | 201 |
| `GET /appointments/:id` | `getAppointment` | 200 |
| `PATCH /appointments/:id` | `rescheduleAppointment` | 200 |
| `POST /appointments/:id/cancel` | `cancelAppointment` | 200 |
| `POST /jobs/reminders/run` | `runReminderPass` | 200 `{ processed }` |
| `POST /webhooks/inbound-messages` | `handleInboundMessage` | 200 for all three results |
| `PUT /test/clock` | `setClock` | 204; the route is only registered with `CLOCK_MODE=test` |

## 10. Infrastructure

- **Config** (`infra/config.ts`, Zod, fails at startup when invalid): `DATABASE_URL`, `PROVIDER_URL`, `PORT` (3000), `CLOCK_MODE` (`test` or unset), `QUIET_HOURS_FROM` (21), `QUIET_HOURS_UNTIL` (9).
- **Clock**: `let fixed: Date | null = null; export const now = () => fixed ?? new Date(); export const setClock = (d: Date) => { fixed = d; };`
- **Startup**: the container runs `prisma migrate deploy` and then `tsx src/main.ts`. `/health` answers 200 only when a query succeeds.
- **Provider client**: `POST {PROVIDER_URL}/messages` with `{ to, text }` and the `Idempotency-Key` header, aborted at 5 s. 200 or 202 → `delivered`; 400 or 422 → `rejected`; 503 → `not_delivered`; 504, any other status, a network error or the timeout → `unknown`. It never throws.
- **Compose**: `api` (3000, `CLOCK_MODE=test`, `PROVIDER_URL=http://provider:4010`) and `db` are added; the `provider` service is not modified.

Tests are written by the `test-writer` agent from signatures and rules, never from the implementation; expected values come from the statement.

### T2. Reminder rules

**Scope.** The five pure functions of section 6: `scheduleReminder`, `beforeSend`, `reminderText`, `afterAttempt`, `parseReply`.
**Owns.** `domain/{schedule,message,retry,reply}.ts`. Nothing reachable through the API, so the reviewer does not run `/verify`.

**Acceptance.**
1. `scheduleReminder`: same local time on the previous day in the clinic zone; the statement's March and October DST cases and the Canary case give the expected instant.
2. A time inside quiet hours moves to their end; `from` o'clock is quiet, `until` o'clock is not.
3. A computed time already in the past becomes `notBefore`, and quiet hours apply again.
4. Not before the appointment → `skipReason: 'too_late'`.
5. `beforeSend`: `too_late`, `no_phone`, `opted_out`, checked in that order.
6. `reminderText`: the exact text of the statement, date and time in the clinic zone.
7. `afterAttempt`: delivered → `sent`; rejected → `failed`; not delivered or unknown → +1 min, then +5 min, then `failed`.
8. `parseReply`: SI and NO regardless of case, accents and surrounding punctuation; anything else is `null`.

**Tests.** Unit. **Depends on** T0.

### T4. Appointments

**Scope.** `POST /appointments`, `GET /appointments/:id`, `PATCH /appointments/:id`, `POST /appointments/:id/cancel`; the four use cases; appointment repository (`create`, `findById`, `lockById`, `update`) and reminder repository (`create`, `cancelPending`).
**Out of scope.** Sending; the webhook; `lockNextDue`, `settle`, `lockLastRemindedByPhone`.

**Acceptance.**
1. Creating → 201 with one `pending` reminder whose `scheduledFor` follows rules 2 to 4.
2. When the reminder does not fit before the appointment it is born `skipped` with `too_late`.
3. Unknown clinic or patient → 404. Patient of another clinic or non-future time → 400.
4. Reading returns the reminders oldest to newest; unknown id → 404.
5. Rescheduling cancels the pending reminder and creates a new one, also when the previous one was already sent.
6. Rescheduling a `confirmed` appointment returns it to `scheduled`.
7. Rescheduling a cancelled appointment → 409. One that already started can be rescheduled.
8. Cancelling leaves the appointment and its pending reminder `cancelled`; repeating it → 200 with no change.
9. Dates in responses are UTC with `Z`.

**Tests.** API. **Depends on** T1, T2.

### T5. Send pass

**Scope.** `POST /jobs/reminders/run`, `runReminderPass`, `lockNextDue`, `settle`.

**Acceptance.**
1. A due reminder is sent once, with the exact text, and becomes `sent` with `sentAt`. One not yet due is untouched.
2. The response reports how many reminders were processed.
3. No phone or not accepting reminders → `skipped` with `no_phone` or `opted_out`, without calling the provider.
4. Appointment already started when sending or retrying → `skipped` with `too_late`.
5. Provider unavailable → retry at +1 min and +5 min; third failure → `failed`. Retries do not wait for quiet hours.
6. Lost response or more than 5 s → retry with the same `Idempotency-Key`; the patient gets one message.
7. Provider rejection (422) → `failed` with no retry.
8. Two concurrent passes do not send the same reminder twice.
9. A cancelled or rescheduled appointment does not send its previous reminder.

**Tests.** API, with the provider's `/admin/rules`. **Depends on** T3, T4.

### T6. Patient replies

**Scope.** `POST /webhooks/inbound-messages`, `handleInboundMessage`, `insertIfNew`, `lockLastRemindedByPhone`.

**Acceptance.**
1. SI confirms the appointment of the last reminder sent to that phone.
2. NO cancels that appointment and its pending reminder.
3. Variants (`Sí`, `SI!`, `no.`) are recognised; other text is ignored with 200.
4. The same `messageId` twice is applied once.
5. Among several appointments of the same phone, the one with the last sent reminder wins, excluding started and cancelled ones.
6. A phone with no applicable appointment → 200 and nothing changes.
7. A body that breaks the schema → 400.

**Tests.** API. **Depends on** T4 to implement; T5 merged to run its tests.
